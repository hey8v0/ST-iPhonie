本文件作为后续开发的产品设计基线。Phase 1 技术验证仍需独立完成并通过安卓真机验收，不得因为本文件提前实施后续阶段。

Phase 2：浏览器本体

1. 用户任务与入口

用户从小手机桌面进入浏览器 APP，可以输入网址、搜索关键词、继续上一次浏览会话、打开最近访问的网站。

进入网页后，可以自然地浏览、输入、滑动、播放视频、管理标签页及分享内容。

正常浏览过程中，用户不需要理解 Firefox、noVNC、RFB、虚拟桌面或输入桥接等底层概念。

2. 复用与风格

沿用小手机现有主题体系 data-theme、data-skin，以及现有语义变量、图标、字体、圆角、列表、按钮和动效。

使用 ui/icons.js 及现有 dialog、menu、confirm、列表、开关、搜索和选择组件。

禁止为浏览器单独创造另一套视觉体系。

日间、夜间、Aero、文艺小清新及自定义主题均需保持各自原有表现。

浏览器界面尽量轻量，避免过度使用卡片、阴影、说明文字和重复操作入口。

3. 页面结构与适配

3.1 浏览器首页

保留当前已经改善的本机 Firefox 连接卡片和最近打开列表。

首页结构：

- 沿用小手机原有 APP 返回及主页导航。
- 顶部设置简洁的搜索与地址输入框。
- 删除独立的前往按钮。
- 原前往按钮的位置替换为更多菜单图标。
- 用户通过输入法回车、搜索或前往键提交地址。
- 删除首页地址栏下方多余的独立操作行。
- 本机 Firefox 连接卡片。
- 最近打开的网站列表。

首页不重复显示浏览状态下的底部工具栏。

本机 Firefox 卡片显示必要的安装及连接状态，不堆叠底层技术信息。安装、故障和诊断说明通过现有帮助或更多入口按需展开。

最近打开使用现有列表交互，显示实际网站图标、标题或域名。缺少图标时使用小手机已有的占位样式，不编造网页信息。

3.2 网页浏览状态

顶部：

- 简洁的地址栏。
- 显示实际网页地址或适当简化后的域名。
- 点击后可以编辑、搜索或输入新网址。
- 使用回车提交，不增加前往按钮。
- 保留必要的加载及刷新反馈。

中间：

- 实际网页内容。
- 不显示 Firefox 桌面窗口标题栏、原生标签栏、原生地址栏。
- 不显示 noVNC 官方悬浮控制栏。
- 不显示常驻输入中转面板。
- 不显示持续占用空间的连接状态栏；正常连接状态无需一直提示。

底部：

参考 Via 的五个主要操作入口，按以下顺序排列：

1. 返回。
2. 前进。
3. 浏览器首页。
4. 标签页。
5. 更多菜单。

标签页按钮显示真实的标签页数量。

浏览状态的更多菜单收纳刷新、分享给 Char、收藏、历史记录、外部打开、手机版与桌面版切换、全屏、备用键盘入口、浏览器设置等操作。

同一操作通常只保留一个主要入口。

3.3 沉浸式浏览

这是浏览器的核心功能，不是可有可无的附加功能。

顶部地址栏和底部工具栏均必须支持收起与恢复。

默认交互：

- 用户持续向下浏览网页时，自动收起地址栏和底部工具栏。
- 用户反向滑动时，恢复相应工具栏。
- 轻微滑动、点击、拖动和输入操作不能反复触发工具栏切换。
- 页面没有可滚动内容时，仍应允许手动隐藏工具栏。
- 更多菜单提供手动隐藏工具栏的操作。
- 收起后提供明确、可发现且不持续占用网页空间的恢复手势或操作。

完全沉浸状态下，浏览区域只显示网页内容。

不能保留原工具栏的空白占位，不能用常驻悬浮控制条替代已隐藏的工具栏，不能因为工具栏收起而失去返回、退出、键盘及分享功能。

由于网页画面来自 Firefox 与 RFB，不能仅依赖外层浏览器容器的 scroll 事件判断真实网页滚动。

结合 Firefox 扩展提供的页面滚动状态、用户手势以及远程画面事件实现交互。

处理滚动方向、触发阈值、动画、重复事件和状态恢复，避免工具栏反复闪烁。

工具栏收起及恢复时，应正确处理网页可用面积、画面尺寸、触摸坐标和远程屏幕调整。避免频繁调整 framebuffer 导致画面跳动、网页重新排版或播放卡顿。

尊重系统减少动态效果设置。

3.4 标签页

参考 Via 的移动端标签页管理方式。

点击底部标签页按钮，打开独立的标签页管理面板。

显示真实标签页的标题、网站图标和当前选中状态。在性能允许时提供对应网页缩略图。

支持：

- 新建标签页。
- 切换标签页。
- 关闭指定标签页。
- 关闭其他或全部标签页。
- 返回当前网页。

批量关闭采用小手机已有的确认方式。

关闭最后一个标签页时，返回浏览器首页。

缩略图不是必须实现的首要功能，不得为生成缩略图频繁切换用户的活动网页。

3.5 手机版与桌面版

默认使用适合手机的浏览模式。

在更多菜单中提供「请求桌面版网页」开关。

切换应真正作用于 Firefox 的网页浏览环境，而不是单纯放大、缩小远程画面。

结合实际 CSS viewport、UA、DPR、网页缩放、浏览器配置和必要的页面重新加载进行实现。

默认优先按当前标签页或站点管理桌面版状态，避免切换一个网站时影响其他标签页。具体持久化方式根据现有浏览器状态架构确定。

不支持移动端布局的网站允许使用桌面模式浏览，不承诺所有网站都能被强制转换成移动版。

不得将 Firefox 开发者工具的响应式设计模式直接作为正式用户交互。

4. 组件与状态

覆盖：

- 未安装。
- 已安装但服务未启动。
- 正在连接。
- 正常浏览。
- 网页正在加载。
- 网页加载失败。
- 连接中断。
- 输入法显示。
- 标签页切换。
- 工具栏收起。
- 沉浸式浏览。
- 视频全屏。
- 手机版与桌面版切换。

正常状态尽量减少技术文案。

失败状态提供明确的下一步，例如重新连接、查看帮助或导出诊断。

操作失败不应清除浏览会话、用户输入或已打开标签页。

5. 操作流程

5.1 地址输入

用户点击地址栏，直接唤起设备原生输入法。

输入网址或关键词，通过回车提交。

真实导航完成后，地址栏与 Firefox 实际页面保持同步。

通过 Firefox 扩展控制真实导航和获取状态，不再将模拟 Ctrl+L、Ctrl+C 等快捷键作为主要实现。

5.2 网页文字输入

目标体验与普通手机 APP 一致。

用户点击网页中的搜索框、文本框、评论框或其他可编辑区域时，应尽可能直接唤起安卓原生输入法。

允许使用不可见但可聚焦的本地输入代理处理 IME 和文字传输。

禁止将独立的 textarea、输入按钮、退格、空格、回车等中转面板作为正常输入方式。

中文选词完成后自动传输实际文字，不需要额外点击发送或输入。

支持英文、中文、数字、Emoji、退格、回车、换行、文本选择及复制粘贴。

正确处理 composition 事件，避免拼音和最终选词重复输入。

输入代理必须管理远程焦点和当前标签页，切换页面或失去焦点时停止向旧输入目标传输文字。

如果安卓浏览器限制异步唤起键盘，可以通过更多菜单中的备用键盘入口，在真实用户手势中直接唤起软键盘，但仍不显示中转面板。

桌面端直接使用用户的物理键盘及系统输入法。

键盘弹出后保持网页文字大小和画面宽度稳定，不允许整张网页缩成一张小图片。必要时调整可视区域或滚动位置，使当前输入区域可见。

5.3 触屏操作

支持正常单击、滑动、长按、拖动、双指缩放及视频进度条操作。

普通手指滑动优先解释为网页滚动，而不是意外拖动鼠标。

明确区分网页手势、工具栏收起手势、标签页操作和系统返回手势。

不能为了增加手势功能而破坏网页原有交互。

5.4 视频全屏

区分：

- 浏览器沉浸式浏览。
- 小手机浏览器全屏。
- Firefox 全屏。
- 网页视频播放器全屏。
- Firefox 画中画。

手机端网页视频进入全屏时，优先切换至横屏显示，并隐藏不必要的工具栏。

在宿主浏览器和系统允许的情况下使用原生全屏与屏幕方向能力。

如果无法锁定屏幕方向，提供合理的横屏显示回退或提示用户旋转设备，不应强制产生错误的旋转画面。

必须提供容易触发的退出全屏方式。

退出后恢复原有浏览方向、工具栏状态及网页位置。

电脑端使用正常桌面全屏体验，不强制旋转屏幕。

分别验证视频声音、画面、进度条和音画同步。VNC 画面播放成功不等于音频传输已经实现。

6. 数据与边界

保留现有 Firefox Profile、Cookie、登录状态、收藏夹、历史记录和已打开的标签页。

保留用户的浏览模式和工具栏偏好。

真实浏览器控制、RFB 画面及输入能力分离，底层实现不得成为常驻用户界面。

Android Termux 为当前优先验收平台。

电脑端纳入架构兼容目标，但需要单独评估 Windows、Linux 和 macOS 的 Firefox 部署、虚拟显示及本地通信方案。不能假设 Termux 安装脚本可以直接在电脑端使用。

未安装本机浏览器服务的平台仍应保留合理的浏览或外部打开入口。

7. 验收

以实际安卓真机交互和视觉结果为主要验收依据。

至少覆盖：

- 首页不存在前往按钮和多余操作行。
- 最近打开占满可用宽度。
- 地址栏与底部工具栏可以隐藏和恢复。
- 沉浸状态下网页真正占满释放的空间。
- 滚动过程中工具栏不会反复闪烁。
- 中文输入不需要可见中转面板。
- 输入法弹出时网页不会被整体缩小。
- 标签页数量、标题和切换来自真实 Firefox 状态。
- 手机版与桌面版切换实际有效。
- 手机视频全屏和横屏体验正常。
- 能够可靠退出全屏。
- 320、360、390 CSS px 及实际更窄容器下无横向溢出。
- 日间、夜间及已有主题下的视觉效果正常。
- 锁屏、后台切换、重连及异常恢复后保留浏览数据。

Phase 3：User 向 Char 分享网页及视频

1. 用户任务与入口

用户正在浏览网页时，可以通过浏览器更多菜单中的分享入口，将当前真实网页分享给指定 Char 或已有群聊。

分享应融入现有聊天体验，而不是新增独立的网页消息系统。

2. 复用与风格

复用小手机现有聊天气泡、消息卡片、好友与群聊选择器、图片预览、确认弹框和消息持久化机制。

网页卡片和视频卡片采用统一设计语言，根据信息类型展示内容。

3. 页面结构与适配

分享预览包含：

- 网页封面或可用缩略图。
- 标题。
- 网站名称。
- 真实链接。
- 可获取的简介。
- 用户附带的文字。
- 分享对象。
- 可选的内容范围。

默认简洁显示基础信息，扩展内容按需展开。

缺少封面、简介或字幕时直接省略相关字段，不生成虚假的页面信息。

聊天中的卡片可以点击打开网页，不在聊天气泡内堆叠完整文章。

4. 组件与状态

区分普通网页、文章、视频、仅链接分享、内容获取失败和部分内容可用。

分享预览必须明确显示 Char 实际能够收到的内容。

网络异常或内容提取失败时，允许用户继续分享已获得的有效信息。

5. 操作流程

用户点击分享，获取当前真实网页信息，选择分享内容，选择私聊或群聊，添加附言并确认发送。

取消或暂时关闭预览时，合理保留未发送的草稿。

对于视频页面，默认获取：

- 标题。
- 视频链接。
- 网站名称。
- 可获取的封面。
- 视频简介。
- 可获取的时长。

按需提供：

- 当前播放时间点。
- 当前画面截图。
- 已获取的字幕或字幕片段。
- 用户选中的网页文字或评论。

可进一步评估用户主动选择视频内容分析的能力，但不作为基础分享功能的必需条件。

分享给群聊时只产生一条正常的共享消息，不为每个群成员重复发送相同卡片。

群聊回复继续遵循现有群聊生成规则、角色性格、人际关系及聊天上下文。不因分享网页而强制所有角色回复，也不额外创造固定的回复人格模板。

Char 可以感兴趣、吐槽、忽略、讨论或提出问题，具体反应由角色设定及当前剧情决定。

6. 数据与边界

用户分享的结构化数据应区分：

- 网页真实元数据。
- 实际提取的正文。
- 生成的摘要。
- 实际获取的字幕。
- 页面截图。
- 用户附言。

Char 不得将收到视频链接等同于观看完整视频。

只有实际获取的文字、图像或字幕才能作为相应内容的依据。

对于支持视觉输入的模型，在用户确认后提供图片。对于不支持视觉输入的模型，使用实际可用的文字信息。

禁止自动读取用户未分享的标签页、私人浏览记录、密码、Cookie 或表单内容。

登录后页面必须由用户主动选择和预览分享范围。

网页内容属于不可信外部数据，不能修改系统提示词或自行触发工具调用。

7. 验收

验证普通网页、文章、视频、无封面页面、内容提取失败等情况。

验证私聊及群聊分享、卡片持久化、点击打开、取消操作和失败恢复。

确认模型实际收到必要内容，而不只是聊天界面上渲染了一张卡片。

确认视频未被完整读取时，模型能够正确区分自己获得了什么信息。

Phase 4：Char 主动联网搜索及网页分享

1. 用户任务与入口

用户可以让 Char 查询真实互联网资料，也可以允许 Char 根据自身性格、对话情境及当前剧情，自主判断是否需要搜索。

联网功能应当辅助自然聊天，而不是将所有角色变成固定模式的搜索助手。

2. 复用与风格

联网设置归入小手机现有设置体系。

复用已有开关、列表选择器、帮助按钮和 API 密钥管理。

不使用裸露的原生 checkbox 或另建密钥管理页面。

搜索过程使用现有聊天折叠组件、消息状态和网页卡片。

3. 页面结构与适配

联网权限默认关闭，用户主动启用。

提供三个搜索模式：

- 关闭：不执行 Char 真实联网搜索。
- 按需搜索：用户明确提出或自然表达查询需求后，Char 可以判断是否需要搜索。
- 自主搜索：Char 可以根据当前对话和角色设定主动判断是否搜索。

用户应能够按适当的聊天范围管理授权，并随时关闭搜索。

搜索方式默认优先考虑不需要额外搜索 API 密钥的浏览器搜索能力。

支持模型原生联网及可选的外部搜索 Provider。

Brave 等搜索 API 不作为使用 Char 联网功能的默认前置要求。

搜索过程显示

搜索过程中，在聊天流中显示一条简洁的状态记录，例如：

正在搜索：土豆火腿肠拌饭的做法

完成后显示类似：

已搜索 · 阅读了 3 个网页

默认折叠详细过程。

展开后可以查看：

- 实际搜索关键词。
- 执行的搜索次数。
- 访问的网页。
- 网页标题及链接。
- 阅读状态及必要的失败信息。

只展示真实的工具执行过程，不展示模型内部推理或虚构的思考记录。

搜索过程记录不能被作为 Char 普通聊天台词反复注入上下文。

4. 组件与状态

支持：

- 联网未启用。
- 正在搜索。
- 正在读取网页。
- 搜索完成。
- 部分结果可用。
- 无有效结果。
- 搜索引擎访问受限。
- 搜索服务不可用。
- 用户取消。
- 超过搜索预算。

用户取消搜索后应停止相应任务，不继续进行后续网页读取。

5. 操作流程

Char 根据用户请求或自身判断提出结构化搜索请求。

系统执行真实搜索，将实际结果返回给模型。

Char 自主选择需要阅读的网页，并根据获得的信息决定是否继续搜索其他关键词或阅读更多网页。

完成后，自然地回应用户，并根据情境分享真实网页卡片。

不要求每次搜索都必须发送链接卡片，也不要求每次聊天都联网。

角色自主决定搜索行为及回应风格，但必须在系统设定的时间、次数、内容长度和费用边界内运行。

群聊中的角色联网行为同样受现有群聊规则与权限控制，避免多个角色重复搜索同一内容。

6. 数据与边界

搜索与用户私人浏览会话隔离。

优先评估独立 Firefox Profile 或其他经过验证的隔离浏览环境，不得占用用户正在观看视频或浏览网页的窗口。

搜索环境不共享用户私人 Cookie 和登录凭据。

建立统一的搜索 Provider 接口：

- 浏览器搜索。
- 模型原生联网。
- 可选第三方搜索服务。

仅在相关 Provider 实际支持时启用对应功能。

模型原生联网必须获得真实工具结果或可验证的来源信息，不允许将模型凭空生成的链接当作搜索结果。

浏览器搜索遇到验证码、访问限制或无法解析页面时，应明确失败并合理结束，不绕过网站安全措施。

搜索模块设置每轮请求次数、网页阅读数量、总时间、上下文长度及重复请求限制。

搜索深度由角色根据需要决定，但必须遵守预算。

防止网页提示词注入、SSRF、未经授权的本地网络访问、任意命令执行及敏感信息泄露。

仅允许搜索和读取经过安全校验的公开网页。

7. 验收

验证 Char 能够：

- 根据用户自然语言需求发起真实搜索。
- 在自主搜索模式下自行决定是否需要联网。
- 阅读多个真实网页。
- 根据实际搜索结果回应。
- 分享能够打开的真实网页卡片。
- 在聊天中展示默认折叠的搜索过程。
- 在失败时诚实说明无法获得结果。
- 在未配置 Brave API 密钥的情况下，通过可用的浏览器搜索方案完成任务。
- 搜索过程中不干扰用户的私人浏览会话。
- 在关闭权限或取消任务后停止搜索。

开发顺序与交付规则

Phase 1 完成后，先等待安卓真机验收。

Phase 2 完成后，先验证浏览器是否真正易用，再进入 Phase 3。

Phase 3 验收分享与群聊闭环后，再进入 Phase 4。

每个阶段独立提交，保留上一阶段的可用版本。

开发成果推送至对应测试分支，不直接合并 main。

涉及 Termux 服务、Firefox 扩展、viewer 或独立安装组件时，同时提供匹配版本的测试安装包。

提供最简单的手机端更新命令及回退方式，避免测试安装过程污染 Git 工作区。

每次交付说明：

- 实际修改内容。
- 复用了哪些已有组件。
- 视觉与交互验证结果。
- 已执行的自动化测试。
- 尚未完成的功能。
- 需要安卓真机验证的内容。

不要用静态截图、模拟数据或语法检查代替实际浏览体验验收。

产品最终目标：

让用户像使用普通手机浏览器一样自然地浏览真实互联网，并能够与 Char 或群聊成员分享真实网页；角色可以在用户授权的情况下自主搜索、阅读和分享信息，而所有底层技术复杂性均由小手机自身负责处理。
